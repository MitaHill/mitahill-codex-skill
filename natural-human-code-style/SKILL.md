# Natural Human Code Style

Write code like an experienced software engineer who has maintained real projects for many years.

The priority is not maximum abstraction or textbook perfection. The priority is:

- readable
- practical
- maintainable
- consistent with existing project style

Avoid producing code that looks generated by AI.

---

## General style

Before writing code:

1. Read the existing project structure.
2. Follow existing naming conventions.
3. Reuse existing patterns.
4. Modify the minimum amount of code.

Do not redesign the entire project unless explicitly requested.

Prefer:
- simple solutions
- boring solutions
- proven patterns

Avoid:
- unnecessary complexity
- over-engineering
- excessive abstraction

---

## Naming

Use natural names that real developers commonly use.

Prefer:

```python
user
users
item
data
config
ctx
req
resp
result
cache
db
```

Avoid overly descriptive or mechanical names like:

```python
user_data_object
item_handler_interface
abstract_factory_manager
processing_result_container
```

---

## Comments

Write comments like a human who has maintained this code.

- Explain **why**, not **what** (the code already says what it does)
- Add comments for non-obvious logic, edge cases, or workarounds
- Remove boilerplate comments like `# This function does X` when the function name already says it
- Include TODO/FIXME/HACK markers for known shortcomings

---

## Functions

- Keep functions short but don't split them into 10 tiny helpers for no reason
- 20-50 lines per function is fine; don't refactor just because a linter says so
- Return early for error cases, keep the happy path clean
- Use descriptive function names but don't make them paragraphs

---

## Error handling

- Handle errors where they happen, not in a central super-handler
- Use try/except for real error paths, not for control flow
- Log errors with enough context to debug without needing a replay
- Don't silently swallow exceptions

---

## Consistency

- Match the existing code style of the project — don't fight it
- If the project uses 2-space indent, use 2-space indent
- If the project uses `snake_case`, don't write `camelCase`
- If the project has no tests, don't add a full test suite unless asked

---

## Imports

- Group by stdlib → third-party → local
- Don't reorganize existing imports unless part of the change
- Import what you need, not everything
