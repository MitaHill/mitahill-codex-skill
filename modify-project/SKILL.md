# Modify Project

## 1. 前期准备

### 1.1 理解项目结构
- 阅读项目 README、配置文件（package.json、Cargo.toml、Dockerfile 等）
- 了解项目使用了什么语言、框架、构建工具
- 查看目录结构，理解各模块职责

### 1.2 理解需求
- 明确用户要修改什么、期望的效果是什么
- 如果有不明确的地方，先澄清再动手

## 2. 代码风格

修改代码时保持自然的人类风格，拒绝 AI 味：

- **命名自然** — 用项目既有命名习惯，不发明新术语
- **注释精炼** — 只写非显而易见的逻辑：边界条件、workaround、TODO/FIXME
- **不重排代码** — 不改格式、不重命名变量、不重新组织 import，除非改动直接涉及
- **融入项目** — 新代码看起来像是项目原有作者写的，而不是一个机器人后补的

> 完整规范见 `natural-human-code-style` skill。

## 3. 核心原则

> **最小改动、最简单实现。** 不改变现有设计风格，融入既有代码习惯。

- 遵循项目的既有代码风格和架构模式
- 不做与需求无关的"顺手优化"
- 不引入新的依赖除非绝对必要
- 保持向后兼容
- **快速失败** — 修改后如果关键依赖或配置缺失，要清晰报错终止，不静默降级
- **日志同步** — 新增错误路径时要附带足够上下文，让运维能定位问题而不用重放

## 4. 模块解耦与原子化

当一个代码模块体积过大、难以维护时，考虑进行解耦和原子化操作。

**但解耦是过程，不是目标。** 目标是让项目更好维护。

- **识别信号** — 单一文件超过 300-500 行、函数/类包含多个不相关的职责、修改一个功能需要改动多处
- **按职责拆分** — 将不同职责拆分为独立模块，每个模块只负责一件事
- **保持接口简洁** — 模块间通过明确的接口通信，减少相互依赖
- **逐步进行** — 一次只拆一个模块，拆完验证不破坏功能，再继续下一个

> 注意：解耦操作应当与功能修改分开提交，避免一次 commit 混杂重构和逻辑改动。

## 5. 开发流程

### 4.1 步骤

1. **项目摸底** — 了解项目的语言、框架、依赖、构建方式
2. **定位改动点** — 找到需要修改的代码位置，理解上下文
3. **设计方案** — 以最小改动的方式设计实现方案，向用户说明
4. **实现** — 进行实际修改，每完成一个逻辑单元进行验证
5. **验证** — 运行现有测试，确保不破坏既有功能
6. **提交** — 使用项目既有的 commit 规范

## 6. 注意事项

- **不改格式** — 不调整代码格式化、不重命名变量，除非与需求直接相关
- **不改架构** — 不重构，不提取公共方法，除非改动需要
- **测试先行** — 如果项目有测试，确保修改后测试通过
- **文档同步** — 如果修改了接口或行为，更新相关文档
- **提交粒度** — 一个 commit 只做一件事，功能/修复/重构分开提交
